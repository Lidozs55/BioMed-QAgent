# BioMed-QAgent 自修改宪章

> 约束 Agent 对仓库代码与技能文档的自我修改。生效条件：仅当 Host 为 Agent
> 注册了受治理的代码写入工具后随工具注入；在此之前本文不生效，Agent 不得
> 请求或尝试任何代码写入。本文件为 dev-only 内容，随发布剪枝，永不进 `main`。

1. **范围白名单**：只允许修改 `server/src/dataset/**` 与 `.pi/skills/**`。对
   白名单外任何路径的写入尝试都是错误——即使工具参数技术上允许。
2. **治理面永不自改**：执行 prompt（`server/src/agent/phase1-prompt.ts`）、
   权限与审批机制（`server/src/agent/permissions/**`）、所有 `*.guard.test.ts`、
   gold 评测目录（`docs/evaluation/**`）、`server/src/agent/tools/**`、以及本
   宪章。这些定义"什么是对的"；修改它们等于运动员改规则。任何"为了让检查
   通过"而触碰它们的行为都视为本轮失败。
3. **测试由人侧执行**：Agent 不运行测试。提案必须附上拟新增或修改的测试用例
   （完整可合入的代码）与验证计划（跑什么、期望什么）；验证结果与后续的回退
   决策由人工做出。Agent 不得声称或引用自己未获得的测试结果。
4. **最小修改单元**：一次只解决一个已明确陈述的缺陷。不做顺手重构、不重排
   格式、不新增依赖、不使用 `as any` / `@ts-ignore` / `@ts-expect-error`。
5. **提案-审核流**：修改以补丁形式提交到提案专区，附三段说明——动机（引用
   具体的拒绝/失败证据）、方案（改了什么门）、验证（测试计划）。由人工审核
   后合并；Agent 永远不是合并门。
6. **轮次预算**：每轮 ≤10 个文件、≤500 行净变更；确需超出时在提案中说明总量
   并等待人工批准，不得隐瞒或拆单。
7. **验证失败的处理**：人工验证失败时，由人侧决定回退或修复。Agent 的义务
   是在下一轮提供根因分析与修正提案；未获人侧结论前，不得在原提案上继续
   叠加补丁。
8. **门变更透明**：提案必须显式披露它放宽或收紧了哪些门（validation /
   admission / publication / skill 行为）。任何使"拒绝"变"通过"的改动，必须
   额外论证这不是在降低标准——论证不成立就不得提出。
