## 6. 问题④：前端主数据预览闪退（**已修复**）

### 6.1 根因
`frontend/src/components/ResultsViewer.tsx` 的 `CsvPreview` 对产物 URL 执行：

```ts
fetch(artifactUrl).then((r) => r.text()).then((text) => parseCSV(text))
```

`r.text()` **全量下载 1.5GB 进浏览器内存**后，`parseCSV`（`csvUtils.ts`，`preview: 101`）才裁到 101 行——**裁切逻辑在传输层之后，形同虚设**，大文件直接 OOM 闪退。`BuildResultsViewer` 同样复用 `CsvPreview`。

### 6.2 修复（已实施）
- `csvUtils.ts` 新增 **`fetchPreviewText(url, byteCap=8MB)`**：流式读取响应至字节上限即 `reader.cancel()`，按最后一个完整换行截断，返回前缀文本；无流（测试 mock）时回退 `response.text()`。
- `ResultsViewer.tsx` 的 `CsvPreview` 改用 `fetchPreviewText`（`BuildResultsViewer` 复用同一组件，自动生效）。
- 单测：`csvUtils.test.ts` 4 例（小文件全量、截断按完整行、达到上限后 cancel、非 2xx 拒绝）。`pnpm vitest run` 通过；`pnpm lint` / `pnpm tsc` 0 错误。

> 说明：8MB 上限可容纳默认 100 行预览（当前行 ~350B → 100 行 ≈ 35KB），留足余量；若未来预览行数上调，字节上限随之调整即可。

## 7. 问题⑤：主数据体积过大分析

### 7.1 事实
- 发布主表 `merged/primary.csv` = **1,477.5 MB**，4,264,650 行 × 21 列。
- 行大小 ≈ 350B，远超"probe + sample + value"的理论值（~60B/行）——约 **5-6 倍膨胀**。

### 7.2 膨胀构成（21 列逐项）

| 类别 | 列 | 每行字节 | 4.26M 行合计 |
| --- | --- | --- | --- |
| 标识列（每行相同） | `record_id`(32) + `dataset_id`(26) + `source_id`(26) + `asset_id`(64) | ~150 | **~640 MB** |
| 溯源列（每行冗余） | `source_logical_file`(~27) + `source_line_number`(~2) + `source_column_index`(~3) + `source_column_name`(~10) + `source_raw_value`(≈value) | ~45 | **~190 MB** |
| 实际数据 | `probe_id` + `sample_id` + `value` + `platform_id` + `gene_id_namespace` + 语义/单位/标志列 | ~150 | ~640 MB |

→ 仅"每行重复的标识/溯源列"就占 **~830 MB（约 56%）**；这些信息本可收敛到 manifest/索引，不必随每行复制。

### 7.3 与"筛出无关数据"的关系
- **探针层面**：4,264,650 行 = 全部 ~54,675 探针 × 78 样本，**含 AFFX 对照探针与大量低/零表达探针**；无任何表达过滤。GPL570 探针中约 1/4 为对照/低信号，可过滤。
- **课题层面（最重要）**：**该主数据 0 行 METTL5**——对"METTL5 癌 vs 癌旁差异"这一课题，发布内容本身即"无关数据"。用户"感觉清洗没做好、需要筛出无关数据"的直觉完全正确，且更尖锐：问题不在"清洗杂质"，而在**数据选型与课题错位**（选了一个测不到 METTL5 的平台做主数据）。

### 7.4 修复方向（设计建议，非本轮实现）
1. **列投影瘦身**：发布主表去掉每行冗余溯源列（`source_line_number/source_column_index/source_column_name/source_raw_value` 等），由 provenance/manifest 承载——预计可减 ~20-30%。
2. **探针过滤**：probe 级构建默认剔除 `AFFX-*` 对照探针；可选按表达量过滤（如 RMA > 某阈值）——预计再减 10-30%。
3. **课题相关性优先**：目标基因不可检测（R3）时，优先换可检测的数据源（如 GEO RNA-seq 系列或 GDC 基因级矩阵），而非发布一个完整但无关的矩阵。
4. **预览侧已修复**（§6）：即使体积未优化，预览也不再闪退。

> 前置：远端已并入 31 个提交（V2 内核重构），旧 `app/pipeline/stages/processing.py` 与
> `_CLEANING_MAX_ROWS` 硬截断已随重构移除，清洗逻辑现位于 `app/datasets/build/`。

### 10.1 清洗层级评估：只做"合法性清洗"，没有"清除无关数据"

V2 清洗 = [canonicalizer.py](backend/app/datasets/build/canonicalizer.py) `canonicalize` +
[integrator.py](backend/app/datasets/build/integrator.py) `integrate`，已确认在 executor op 链中
真实执行（非纸面逻辑）。但全部动作都是**行级语法/合法性**：

| 动作 | 层级 | 位置 |
| --- | --- | --- |
| namespace 授权（ENSG/symbol/geo_probe；无声明时拒绝 AFFX 冒充 gene_symbol） | 合法性 | `authorize_namespace` |
| unit / value_semantics / value_scale 白名单 | 合法性 | `canonicalize` |
| 非有限值过滤 | 语法 | `canonicalize` |
| probe→gene 映射（**映射不到的探针原样保留为 geo_probe**） | 命名 | `canonicalize` |
| 列投影（只输出 schema 列） | 结构 | `canonicalize` |
| 行身份去重 | 结构 | `integrate` |
| validation：列数/必填/数值/provenance 缺失 | 完整性 | `profiles.py` |

**缺失的"清除无关数据"（语义层）**：
1. **无相关性过滤**：不检查目标基因（METTL5）是否可检测——coverage=0 只出 warning
   （`_probe_coverage_warnings`，warning-only），1.48GB 无关主数据照常发布。
2. **无探针质量过滤**：AFFX 对照探针、无注释/低表达探针全部保留。
3. **无样本级过滤**：无按课题分组的样本筛选入口。
4. **无统计清洗**：无低表达/高缺失/异常值过滤（仅 `non_finite` 字面过滤）。
5. **无体积/行数上限**：旧 `_CLEANING_MAX_ROWS` 随重构消失且**无替代**——4.2M 行全量直通发布。

**结论**：清洗管线是"清洗不合法数据"而非"清洗无关数据"。ISSUES.md 中 `_CLEANING_MAX_ROWS`
条目（指向已不存在的 `pipeline/stages/processing.py`）已过期，需更新或标记解决。

### 10.2 调研结果不进最终产物（新缺口）

publication artifact 角色仅 5 类：`primary_dataset` / `supporting_dataset` / `schema` /
`provenance` / `audit_report`（[manifest.py](backend/app/datasets/build/manifest.py)）。
**无"调研综述/研究报告"类角色**——LLM 的调研结果（文献结论、选库理由、关键发现）只存在于
任务消息流（events.jsonl），不产出任何可下载文件。建议新增 `research_report` artifact 角色，
由 Agent 在汇报时写盘（结构化 markdown/json），随 publication 发布。

### 10.3 LLM 自主清洗：方向确认（2026-08-11）

架构约束：AGENTS.md"Agent 从不直接组装最终数据集文件"+ V2 确定性 release-invariants 门，
**LLM 直接改数据文件违反审计/可复现铁律**。确认方向：
- **预设工具链 = 指令式清洗**（推荐）：LLM 产出结构化清洗指令（排除规则+理由，如剔除
  AFFX/无注释探针、指定样本子集），确定性内核执行并写清洗审计（规则全文进 provenance）。
- **LLM 自主脚本 = 允许扩展**：LLM 可提交处理脚本（确定性执行、脚本全文进 provenance 审计）。
  这是"代码即审计痕迹"路线，需沙箱边界与脚本版本记录。
- 实施顺序建议：先 10.2 的 `research_report` 角色（成本最低），再指令式清洗工具，最后脚本扩展。

### 10.4 前端加载优化（本次已实施，质量门全绿）

针对"打开对话一次性全量加载慢 / 流式裁切早期消息 / 滚动触发加载更早"，三段式落地：

1. **事件重放窗口化**（[controller.ts](frontend/src/runtime/controller.ts)）：冷启动只重放尾部
   `EVENT_REPLAY_WINDOW_SIZE=3000` 事件（此前从 sequence 0 全量重放全部事件逐条 reduce）；
   更早消息经 snapshot 的 `older_messages_cursor` 从后端分页补齐。重放前将 `lastSequence`
   前移到窗口下沿，避免 reducer 连续性检查误判 gap。单测：`windows a cold event replay to the
   tail when the event log is long`。
2. **timeline 容量上限**（[reducers/shared.ts](frontend/src/runtime/reducers/shared.ts)
   `ITEMS_CAP=500` + [reducers/index.ts](frontend/src/runtime/reducers/index.ts)）：事件应用后
   裁掉最旧 items（流式永不自行移除），`itemSequences` 同步裁剪；更早消息仍可从后端翻页恢复。
   单测：`caps the rendered timeline and drops the oldest items past ITEMS_CAP`。
3. **滚动触发加载更早消息**（[ChatPanel.tsx](frontend/src/components/ChatPanel.tsx)）：
   IntersectionObserver 监听 `older-messages` 哨兵，滚动到顶自动 `loadOlderMessages`，
   按钮保留为键盘可达兜底。测试 setup 补 `IntersectionObserver` mock。单测：
   `auto-fetches earlier messages when the older-messages sentinel scrolls into view`。

未做（用户确认暂缓）：ConversationList 渲染虚拟化（现有 `content-visibility:auto` 已部分缓解）。
