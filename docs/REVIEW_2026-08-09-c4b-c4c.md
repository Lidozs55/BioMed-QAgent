> 来源：LEFTOVERS.md C4b/C4c（P2 批次 Task 8，设计先行）。结论：**两项均 🔒 关闭（带证据）**，无代码改动。

## C4b — coverage<1.0 时 per-binding 排除

**现状（代码证据）：**
- 覆盖门禁位于验证 profile 的 `_check_probe_coverage_required_gene_level`
  （`backend/app/datasets/build/profiles.py:400-443`）：要求合并主表 residual
  `geo_probe` 行为 0 **且** 每个 binding 的 `ProbeMappingSummary.coverage_ratio`
  `math.isclose(1.0, rel_tol=0.0, abs_tol=1e-9)`，否则 profile FAILED → publish 拒绝
  → 整 build NO_DATA。
- 门禁 docstring 明示：*"The 1.0 requirement is server-owned output-integrity
  semantics (D4), never a calibrated threshold the Agent can pass."*
  （profiles.py:406-408）。
- **per-binding 拒绝已存在但只覆盖"零贡献"情形**：
  - `expression_runner.py:470-496`：binding 产生 0 有效行（`row_count == 0`）或
    gene-required build 无任何可发布 gene 行（coverage 为 0）→
    `BindingRejectedError`（`no_primary_data` /
    `REASON_PROBE_MAPPING_UNAVAILABLE_REQUIRED_GENE_LEVEL`）。
  - `_canonical_results_for_bindings`（expression_runner.py:528-536）：被拒 binding
    不进 phase B，provenance 只覆盖存活 binding（expression_runner.py:574-578）。
  - 工具面 `dataset_build_tool.py:613-635`：有 rejected 时 `PARTIAL_SUCCESS` +
    `rejected_sources`（wave-7 语义，test_dataset_build_tool.py:471 锁定）。
- 测试锁定整 build 失败语义：`test_gene_profile_coverage_below_one_fails`、
  `test_gene_profile_zero_coverage_fails`、`test_gene_profile_residual_geo_probe_rows_fail`
  （tests/test_dataset_profiles.py:438-476，均断言 FAILED）。

**语义分析（为什么 partial coverage 不能 per-binding 排除）：**
- 零 coverage（现有拒绝路径）：binding 无任何可用 gene 行，排除**不丢失已映射数据**，
  且以 `rejected_sources` 显式告知用户 → partial_success 语义成立。
- **partial coverage（0<x<1.0）与零 coverage 是质的不同**：binding **有**可用映射行
  已进入合并主表。门禁同时扫描**合并主表**的 residual `geo_probe` 行——若排除该
  binding，其行（含 residual）整体离开主表，映射成功的行被**静默丢弃**，主表看起来
  "完整"而用户的该来源数据缺失 → **数据丢失伪装成成功**，比响亮 NO_DATA 更糟。
- D4 设计意图（profiles.py 与测试 docstring）：*"a partial probe→gene mapping cannot
  masquerade as a complete gene-level dataset"* — 完整性是二进制（1.0 = 完整），不是
  质量刻度；用户请求的 gene 级数据未完整交付时，响亮失败是唯一诚实结果。
- LEFTOVERS C4b 原文已标记 **"接受"**（整 build NO_DATA 与 wave-7 一致）。

**决策：🔒 关闭（不改代码）。** per-binding 排除仅对"零贡献 binding"语义正确（已实现）；
对 partial coverage 排除=静默数据丢失，与 D4 输出完整性语义矛盾。整 build NO_DATA
是 partial coverage 的正确行为。**无新代码。**

## C4c — probe 覆盖阈值校准门槛

**现状（代码证据）：**
- 唯一阈值是 `coverage_ratio == 1.0`（精确相等，profiles.py:419）。
- **双档策略矩阵已交付**（即设计中的"校准机制"）：
  - `gene_expression.release.v1`（gene，`required_entity_level="gene"`，profiles.py:139-140）
    → 严格 1.0，不达标 FAILED。
  - `gene_expression.probe_release.v1`（probe，`required_entity_level="probe"`，
    profiles.py:543）→ **任何 coverage 可发布**，仅 warning
    （`_probe_coverage_warnings`，profiles.py:450-478）。
  - 两者均在 `VALIDATION_PROFILES` 注册（profiles.py:565-569）；spec 的
    `target_entity_level`（contracts.py:297-298）经 profile 的 `required_entity_level`
    驱动实体级兼容检查（profiles.py:156）。
- 仓库内**无真实数据集覆盖分布**可校准中间阈值：fixture GDC + 合成测试数据
  （test_dataset_expression_runner.py 仅 1.0 与 0.5 两个合成样例）。

**语义分析（为什么中间阈值不可校准也不该存在）：**
- 1.0 不是质量刻度而是**完整性**判定（D4）：probe 映射到 gene 失败 = 失败行，不是
  低质量行。中间阈值（如 ≥0.85）会允许"部分映射伪装成完整 gene 数据集"——
  与 D4 docstring 直接矛盾。
- 实体级矩阵（gene 严格 / probe 放宽）已是完整的策略设计；额外阈值档是
  **gold-plating**（Global Constraints 明确禁止）。
- 校准需要真实生产分布（先采集数据），当前无此数据源；即使有，也应在产品层面
  决定"接受多少未映射率"——属产品决策而非代码校准。

**决策：🔒 关闭（不改代码）。** 阈值校准无数据基础且与 D4 完整性语义冲突；双档
实体级策略矩阵是既定交付。若未来产品要求中间档，先建立真实覆盖分布的数据采集
路径（LEFTOVERS 记录该前置条件）。
