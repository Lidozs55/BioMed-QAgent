## 0. 核心架构性缺陷（根因收敛）

**核心问题**：`TaskManager._execute` 的"成功证据校验"完全缺失。

`backend/app/runtime/manager.py:1201-1212`：

```python
execution.seal_completion()
completion_events = await execution.commit_completion()   # 可能返回 []
for completion_event in completion_events:
    await self._append_completion_status(accepted, completion_event.payload, ...)
await self._append_completion_status(accepted, RunCompletedPayload())  # 无条件发射
```

`RunCompletedPayload`（`backend/app/domain/contracts/events.py:179-181`）是**空 payload**，无 validation 字段、无 artifact 引用、无 final_output 内容、无 finish_reason。一旦 `run_executor` 返回无异常，manager **无条件**发射 `RunCompletedPayload`，不校验是否真的产出了任何东西。

这一缺陷同时导致：
- 第 1 节（LLM 完成后部分案例结果未显示）
- 第 2 节（LLM 截断却标记为 COMPLETED）

**单一最高杠杆修复点**：在 `manager.py:1201-1212` 之间，AGENT 模式下增加"成功证据校验"：至少 1 个 `artifact_produced` 事件 + final_output 非空。不达标转 `RunFailedPayload`。这一改动能同时解决两个核心症状。

## 1. LLM 完成后部分案例"结果"未显示（P0）

### 1.1 根因链路

1. Agent 模式下，`_load_artifact_payloads`（`backend/app/agent_loop/runner.py:104-133`）在两种情况下**静默返回 `[]`**：
   - `run_manifest.json` 不存在（LLM 没调 `run_research_pipeline` / pipeline 失败 / 被取消）
   - `manifest_fingerprint == previous_fingerprint`（同 task 二次 run，内容未变）
2. `if payloads:` 守卫（`runner.py:284-305`）导致 `set_completion_committer` 未被调用，`_completion_committer` 保持 `None`
3. `commit_completion()` 返回 `[]`，但 `manager.py:1209` 仍发射 `RunCompletedPayload`
4. 前端收到 `run_completed` 但从未收到 `artifact_produced`
5. HTTP `list_artifacts`（`backend/app/api/routes.py:538-604`）因为 `.runtime-publication.json` 标记不存在，**永远返回 `[]`**
6. 前端 `ResultsViewer.tsx:274-282` 显示"暂无结果"

### 1.2 次要假设

- **假设 B**：WS `run_manifest` artifact_produced 事件的 RESET 逻辑（`frontend/src/runtime/reducer.ts:890-912`）与 HTTP hydration 存在竞态，WS gap 补传失败时 CSV 永远不回填
- **假设 C**：`_emit_activity` cancellation 守卫（`manager.py:1340-1350`）在 cancel + completion 同时发生时丢弃 `ArtifactProducedPayload`

## 2. LLM 截断但流水线状态变为"完成"（P0）

### 2.1 根因链路

1. `build_agent`（`backend/app/agent_loop/agent.py:112-117`）构造 Agent 时**未设置**：
   - `output_type`（对比 summarizer 有校验）
   - `input_guardrails` / `output_guardrails`
   - `max_turns`（对比 `compaction.py:239` summarizer 显式 `max_turns=1`）
2. `_build_delegate`（`backend/app/agent_loop/model.py:29-38`）不传 `max_tokens`，LLM 默认截断时 DashScope 返回 `finish_reason="length"`
3. `_consume_events` 完成判定只有 `except StopAsyncIteration: return`（`runner.py:189-190`），不读 `result.final_output`、不读 `finish_reason`
4. `_extract_text_delta`（`runner.py:440-459`）只读 `delta.content`，**完全忽略 `finish_reason`**
5. OpenAI Agents SDK 在 `finish_reason="length"` 时**不抛异常**，把 partial content 当 `final_output` 返回
6. manager 同第 1 节的"无条件 RunCompletedPayload"路径
7. INSTRUCTIONS 中"必须调用 run_research_pipeline"（`agent.py:36`）是**软约束**，Agent 完全可以只生成讨论文字就结束

### 2.2 5 条 silent-completed 路径

| 假设 | 触发条件 | 优先级 |
|---|---|---|
| H1 | LLM `max_tokens` 截断，SDK 不抛异常 | 最高 |
| H2 | LLM 不调 tool 直接生成讨论文字结束 | 高 |
| H3 | SDK 默认 `max_turns` 用尽（约 10） | 中 |
| H4 | `run_research_pipeline` 抛异常被 LLM 吸收 | 中 |
| H5 | Agent `final_output` 为 None，executor 不校验 | 低 |

### 2.3 关键代码位置

| 主题 | 文件:行号 |

| `Runner.run_streamed` 调用点 | `backend/app/agent_loop/runner.py:263-269` |

| 优先级 | 修复点 | 改动 |

## 6. Follow-up Loop 循环控制完全缺失（P0）

### 6.1 现状

代码库中**完全不存在** follow-up 搜索机制。grep `followup|follow_up|IterationDecision` 在 `backend/app/` 下零匹配（除 `ws_events.py` 的 `task_not_found` 错误码外）。

### 6.2 缺陷（与 project_memory 硬约束冲突）

- **无 `followup_search` status 标识符**：`RunContext.log_query`（`context.py:229-240`）只记录 `query/source/status/records_count`，各 skill 自由使用 "ok"/"failed"/"error"/"succeeded"/"completed" 等不一致状态，**无 `not_found` 标准状态**

- **`IterationDecisionAgent` 已被 project_memory 硬约束要求"完全移除"**——但当前实现是根本没有 IterationDecision 机制，既未实现也未明确文档化"为什么不实现"

### 6.3 修复方案

| 优先级 | 修复点 | 改动 |
|---|---|---|

## 8. 并发与资源管理（P1）

### 8.1 现状

- `artifacts/` 并发写：`publish.lock`（`validation.py:116-121`）保护同 task 的发布；跨 task 因目录隔离无冲突

## 11. Agent max_turns 谨慎设置（P1，需评估）

### 11.1 现状

`backend/app/agent_loop/agent.py:112-117` 构造 Agent 时**未设置 `max_turns`**，使用 OpenAI Agents SDK 默认值（约 10）。这导致两个问题：
- LLM 可能无限调用工具循环（虽未观察到，但理论上可能）
- LLM 可能干到一半被默认 max_turns 用尽截断，但 SDK 不抛异常，走 silent completed 路径（见第 2 节 H3）

### 11.2 谨慎设置原则

**不能简单设置一个较小值（如 5）了事**，因为：
- 复杂研究任务可能需要多轮工具调用（discovery + acquisition + processing + validation 各 1 轮 = 4 轮，加上 followup 可能 6-8 轮）
- 设置过小会导致正常任务被截断
- 设置过大失去保护意义

**建议方案**：
1. **分层设置**：主 Agent `max_turns=15`（覆盖正常 4-8 轮 + followup 3 轮 + 余量），summarizer 保持 `max_turns=1`
2. **达到 max_turns 后的处理**（**用户明确要求**）：
   - **不直接转 FAILED**，而是发射 `UserInputRequiredPayload(prompt_kind="max_turns_reached")` 暂停 Run，进入 `AWAITING_USER_INPUT` 状态
   - **前端展示"继续工作"按钮**：用户点击后调用 `POST /api/v1/tasks/{task_id}/runs/{run_id}/resume`，Agent 从当前会话状态继续执行下一轮
   - **用户也可选择"停止"**：转 CANCELLED
   - **复用 §4.2.1 已完成的 pause-resume 底层架构**（`_await_user_input` 原语），不另建机制
3. **同时实现第 2 节的 finish_reason 校验**：max_turns 用尽与 LLM 截断是不同场景，但都需可观测

### 11.3 关键代码位置

| 主题 | 文件:行号 |
|---|---|
| Agent 构造无 max_turns | `backend/app/agent_loop/agent.py:112-117` |
| 对比 summarizer max_turns=1 | `backend/app/runtime/compaction.py:239` |
| `_await_user_input` 暂停原语 | `backend/app/pipeline/runner.py`（见 §4.2.1） |
| `UserInputRequiredPayload` | `backend/app/domain/contracts/events.py` |
| `POST /resume` API | `backend/app/api/routes.py` |
| 前端 `UserInputDialog` | `frontend/src/components/UserInputDialog.tsx` |

### 11.4 修复方案

| 优先级 | 修复点 | 改动 |
|---|---|---|
| P1 | `agent.py:112-117` | 设置 `max_turns=15`（覆盖正常 + followup + 余量） |
