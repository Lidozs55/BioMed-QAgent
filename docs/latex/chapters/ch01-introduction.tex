\chapter{引言}

\section{科研数据整理的真实困境}

生物医学研究中，"找到数据"不等于找到能用的数据。一个可以直接分析的数据集，至少要回答六个问题：(1)覆盖哪些实体和样本、(2)来自哪个版本、(3)原始文件如何变成当前字段、(4)不同来源能否在同一层级合并、(5)哪些值存在冲突、(6)哪些判断需要研究者确认。现有流程的核心问题不在效率，而在可信度。

第一，多源数据的含义不自动一致。相同列名可能代表不同测量，不同列名也可能是同一概念；基因、变异、化合物各有标识体系。表达数据中，探针级与基因级是不同的行层级（表中一行代表什么观测单位），原始强度、归一化值和对数值不能仅凭列名拼接。生物活性数据的化合物身份、实验类型和单位需要显式映射，冲突要显式记录。

第二，可读信息不等于可计算数据。论文中的PDF表格、扫描图、折线图和补充XLSX需要不同解析方法。视觉模型可以读图表，但模型输出本身具有非确定性——若不保留页码、边界框、模型身份、提示版本和置信度，就无法复核。

第三，人工复制整理难以复现。常见流程是在浏览器、Excel、脚本和聊天窗口间复制内容。即使最终得到CSV，也常缺少原始文件摘要、检索条件、字段映射、被拒绝行、冲突处理和程序版本。发现错误时，研究者难以判断应修改哪一步。

第四，一次性问答无法承担长流程状态。数据任务可能因下载、权限、人工确认或服务故障跨越多个会话。普通的对话式问答把中间状态留在上下文窗口（模型单次能容纳的对话内容），一旦超时或重启，模型容易重复下载、改变处理方式或遗忘指令。

第五，数据来源分散且异构。同一研究问题可能同时涉及PubMed论文、GEO表达数据、ClinVar变异证据、PDB蛋白信息，以及论文附件或网页。不同平台的查询语法、分页方式、访问限制和版本标识各不相同。"相关页面"通常易于查找，但研究者难以证明是否覆盖应查来源、是否遍历分页、是否遗漏补充材料。

\section{相关工作的实际缺口}\label{sec:related}

四类系统分别解决了部分问题，但留下核心缺口。

第一类是检索系统。PubMed、GEO、GDC、UniProt、ClinVar、ChEMBL等提供标识稳定、字段规范的入口，但跨库研究仍需手工组合查询并下载文件。通用网页搜索可以发现API未覆盖的页面和附件，却不能保证搜索排名反映数据质量。

第二类是解析工具。规则解析器处理固定格式时容易复现，但难以覆盖布局复杂的非结构化内容。OCR与视觉语言模型（多模态大模型，可直接读图像）更加泛用，但识别精度有限。

第三类是整合与溯源系统。传统ETL擅长映射固定的输入输出结构，但难以处理运行时才确定的开放来源集合——例如执行到一半发现需补充某篇论文的附件数据，固定管线必须修改代码后重排重跑。W3C PROV、FAIR、OpenLineage等描述和观测"溯源应当是什么样"，但不负责生成、校验或阻止无溯源发布。

第四类是LLM辅助系统。检索增强生成、工具调用和ReAct等方法使模型能在回答前搜索外部信息并调用工具。LangChain、AutoGen、OpenAI Agents等框架以模型自报、对话结束或工具返回值界定"完成"，不设"产物哈希重验失败即拒绝展示"的正式门\cite{langgraph,autogen,openai-agents}。DocETL、Palimpzest等声明式LLM数据管线中，LLM生成的算子与表结构在进入最终产物前没有信任边界，其校验停留在准确度层面，最终输出也只是普通文件\cite{docetl,palimpzest}。Temporal、Airflow等工作流引擎的人工任务节点不绑定证据摘要\cite{temporal-approval}。

综合来看，现有系统要么把可信度留给研究者自行判断，要么把模型输出直接当成数据——若直接让模型生成或改写正式数据，仍会面临幻觉、不可重复和长流程状态脆弱等问题。

\section{本系统的核心目标}

BioMed QAgent不是"替研究者得出科学结论"，而是完成位置更上游的一步：将自然语言研究目标转换为结构化科学数据产品。该产品可以继续用于分析，能够追溯来源、检查质量，并可根据反馈修正。

系统试图解决四个连续问题：

\begin{enumerate}
  \item 根据研究目标定位合适的论文、数据库、附件、表格或图像数据（Agent侧的需求编译与来源发现）；
  \item 把异构载体解析为明确表结构和行层级下的规范记录（Core的解析、规范化阶段）；
  \item 在不掩盖缺失、重复、单位差异和身份冲突的前提下完成多源整合（Core的兼容、整合、派生阶段）；
  \item 将每一步的来源、输入摘要、处理版本、质量判断和人工修正一起发布，使结果能被验证和复用（Core的校验、发布阶段与可持久化人工确认）。
\end{enumerate}

系统的工程投入集中在赛题要求的核心链路——来源发现与覆盖、异构解析、清洗整合、图表提取与全链路溯源。我们有意不把科研分析和结论生成纳入正式完成标准，这样既符合赛题1A的任务边界，也避免将"数据是否正确"与"模型解释是否听起来合理"混在一起。

\section{研究问题与数据需求}

本文要解决的核心问题是：用户以自然语言提出的研究需求，能否被系统可靠地转换为定义明确、过程可控且结果可复核的数据交付？

用户最初输入的是一段自由文本。系统不试图完整定义全部科学意图；这既不可能，也没必要。系统只固定那些"一旦改变，数据产品的含义就会随之变化"的关键选择。这些选择共有十项（表~\ref{tab:spec-choices}），在实现中对应数据集执行规格（DatasetExecutionSpec）结构。

明确这十项之后，同一份需求就可以被反复执行、逐项核对和事后审计，不会因表述含糊而产生不同的结果。

相应地，系统交付的也不是一张孤立的数据表。合格的候选结果必须同时包含六类信息：(1)数据本身、(2)表结构、(3)溯源信息、(4)审计记录、(5)验证结果、(6)文件清单。候选结果只有通过全部质量门检查后，系统才会生成正式发布版。正式发布只新增版本、不覆盖既有发布；读取时，系统依据发布清单重新校验文件摘要，发现文件缺失、损坏或与清单记录不一致即拒绝展示。

\section{主要贡献与核心机制}\label{sec:contributions}

本文将实际完成的功能归纳为三个相互关联的系统贡献。它们都建立在同一机制之上：从来源字节到发布物逐文件计算SHA-256，并在读取时重新校验，形成贯穿八阶段流水线的证据链。

\textbf{贡献一：将任务完成绑定到唯一可验证的产物，而不是模型自报。}主流 Agent 框架（如第二章所述 LangChain、AutoGen 等）以模型自报、对话结束或工具返回值界定"完成"，不设"产物哈希重验失败即拒绝展示"的正式门。本系统把正式完成定义为唯一可达的不可变发布物。

完成规则写入系统提示，运行时逐回合注入"尚无正式发布物""仍有工具在执行"等进度真相，终态一律拿不准就拒绝（fail closed）。这是对"执行幻觉"（自报完成、产出为空壳或伪造行）的结构性对策。早期对抗测试中，某代 Qwen 模型（qwen3.7-plus）曾连续三轮谎报任务完成，占位符空壳是内容筛查上线前唯一一次穿透，上线后未再发生。

\textbf{贡献二：表结构可以在运行时申请进入，但准入权始终在Core。}声明式LLM数据管线中，LLM生成的算子与表结构在进入最终产物前没有信任边界。本系统允许未注册的多表结构"申请进入"，但须通过限定准入检查（输入角色、可物化性、输出精确完整）。候选字节在隔离区逐文件重算摘要，且变换方在代码级无法选择校验、评估与发布模块。因此，开放输入不会扩大写入权限（实证见gold7 案例（第五章评测案例之一）预检11次结构化拒绝后的正式完成）。

\textbf{贡献三：将人工确认与证据绑定，支持恢复，并保留版本历史。}工作流引擎的人工任务节点不绑定证据摘要。本系统的审批请求携带覆盖其对象的证据摘要；如果响应与任务身份不符，系统就拒绝恢复。动态发布、图表证据、浏览器证据接受等需要发布验收的场景不可绕过，且强制人工确认。修正通过supersedes关系形成新版本，而不是覆盖旧产物。

\textbf{核心机制总结}：这三项贡献的实现依赖统一的证据链机制——来源文件摘要（SHA-256）→ 解析记录 → 规范化记录 → 兼容性检查 → 整合审计 → 校验报告 → 发布清单，每个环节都留下可重验的摘要。读取时重新计算摘要，不匹配即拒绝展示。这条链路确保：无法证明正确的候选进不了正式数据，能证明正确的决策全部由Agent自主完成。
