\chapter{引言}

\section{科研数据整理的真实困境}

生物医学研究中，“找到数据”不等于找到能用的数据。一个可以直接分析的数据集，至少要回答六个问题：覆盖哪些实体和样本、来自哪个版本、原始文件如何变成当前字段、不同来源能否在同一层级合并、哪些值存在冲突以及哪些判断需要研究者确认。现有通用智能体流程的核心问题不在效率，而在可信度。

第一，同一类研究的不同数据集的数据结构可能不一致。相同列名可能代表不同测量，不同列名也可能是同一指标；基因、变异、化合物各有标识体系。另外，在表达数据中，探针级与基因级是不同的行层级，表中一行代表的观测单位不同，原始强度、归一化值和对数值不能仅凭列名拼接。生物活性数据的化合物身份、实验类型和单位需要显式映射，冲突要显式记录。

第二，可读信息不等于可计算数据。论文中的PDF表格、扫描图、折线图和补充XLSX需要不同解析方法。视觉模型可以读图表，但模型输出本身具有非确定性——若不保留页码、边界框、模型身份、提示版本和置信度，就无法复核。

第三，人工复制整理难以复现。常见流程是在浏览器、Excel、脚本和聊天窗口间复制内容。即使最终得到CSV，也常缺少原始文件摘要、检索条件、字段映射、被拒绝行、冲突处理和程序版本。发现错误时，研究者难以判断应修改哪一步。

第四，一次性问答无法承担长流程状态。数据任务可能因下载、权限、人工确认或服务故障跨越多个会话。普通的对话式问答把中间状态留在模型单次能容纳的上下文窗口中，一旦超时或重启，模型容易重复下载、改变处理方式或遗忘指令。

第五，数据来源分散且异构。同一研究问题可能同时涉及PubMed论文、GEO表达数据、ClinVar变异证据、PDB蛋白信息，以及论文附件或网页。不同平台的查询语法、分页方式、访问限制和版本标识各不相同。“相关页面”通常易于查找，但研究者难以证明是否覆盖应查来源、是否遍历分页、是否遗漏补充材料。

\section{相关工作的实际缺口}\label{sec:related}

面对数据查找整合的问题，当前已经存在数种解决方案。主要可以分为下面四类系统。它们分别解决了部分问题，但各有局限。

第一类是检索系统。PubMed、GEO、GDC、UniProt、ClinVar、ChEMBL等数据库平台提供标识稳定、字段规范的入口，但跨库研究仍需手工组合查询并下载文件。第二类是解析工具。规则解析器处理固定格式时容易复现，但难以覆盖布局复杂的非结构化内容。OCR与视觉语言模型更加泛用，其中视觉语言模型是一类可直接读取图像的多模态大模型，但识别精度有限。第三类是整合与溯源系统。传统ETL擅长映射固定的输入输出结构，但难以处理运行时才确定的开放来源集合——例如执行到一半发现需补充某篇论文的附件数据，固定管线必须修改代码后重排重跑。W3C PROV、FAIR、OpenLineage等标准描述了“溯源应当是什么样的”，但不负责生成、校验或阻止缺少溯源的发布。第四类是LLM辅助系统。检索增强生成、工具调用和ReAct等方法使模型能在回答前搜索外部信息并调用工具。LangChain、AutoGen、OpenAI Agents等框架以模型自报、对话结束或工具返回值界定“完成”，没有“产物哈希重验失败即拒绝展示”的验证流程\cite{langgraph,autogen,openai-agents}。DocETL、Palimpzest等声明式LLM数据管线中，LLM生成的算子与表结构在进入最终产物前没有信任边界，其校验停留在准确度层面，最终输出也只是普通文件\cite{docetl,palimpzest}。而Temporal、Airflow等工作流引擎的人工任务节点也不绑定证据摘要，不能记录最终数据的来源与可信程度\cite{temporal-approval}。

综合来看，现有系统要么把可信度留给研究者自行判断，要么把模型输出直接当成数据——若直接让模型生成或改写正式数据，仍会面临幻觉、不可重复和长流程状态脆弱等问题。

\section{本系统的核心目标}

BioMed QAgent不是“替研究者得出科学结论”，而是聚焦于做好数据获取与处理，将自然语言研究目标转换为结构化、可信的科学数据。系统生成的数据表可以继续用于分析，能够追溯来源、检查质量，并可根据反馈修正。

系统试图解决四个连续问题：

\begin{enumerate}
  \item \textbf{找得到}：根据研究目标定位合适的论文、数据库、附件、表格或图像数据。例如研究者需要 EGFR 突变体抑制实验的活性数据，系统能够定位目标数据库与相关补充材料，而非人工逐个站点检索；这一步由 Agent 侧的需求编译与来源发现完成（见 \ref{sec:requirement-compile}--\ref{sec:source-discovery} 节）；
  \item \textbf{读得懂}：把异构载体解析为明确表结构和行层级下的规范记录。论文附表、扫描图与 Excel 格式各异，解析后统一落到同一套表结构上：字段含义与行层级均明确固定，一行究竟代表一个探针还是一个基因由表结构显式声明，不依赖模型推断；相应工作由 Core 的解析与规范化阶段承担（见 \ref{ch:dataset-core} 章）；
  \item \textbf{合得上}：在不掩盖缺失、重复、单位差异和身份冲突的前提下完成多源整合。同一化合物在不同数据库中的标识可能不同，活性单位也可能分别采用 nM 与 µM；整合不抹平这些差异，而是显式换算可转换的量纲、记录其余冲突；这些处理由 Core 的兼容、整合与派生阶段实现（见 \ref{ch:dataset-core} 章）；
  \item \textbf{查得清}：将每一步的来源、输入摘要、处理版本、质量判断和人工修正一起发布。数据使用者可以沿发布清单回溯每个值的来源与处理过程；无法自动判定的差异交由人工确认，不与未决问题一同交付；上述机制由 Core 的校验与发布阶段以及可持久化的人工确认提供（见 \ref{ch:dataset-core} 章与 \ref{sec:hil} 节）。
\end{enumerate}

系统的工程投入集中在赛题要求的核心链路——来源发现与覆盖、异构解析、清洗整合、图表提取与全链路溯源。我们有意不把科研分析和结论生成纳入正式完成标准，这样既符合方向1A的任务边界，也避免将“数据是否正确”与“模型解释是否听起来合理”混在一起。

\section{研究问题与数据需求}

本项目要解决的核心问题，是把用户以自然语言提出的研究需求，可靠地转换为定义明确、过程可控且结果可复核的完整数据表。

用户最初输入的是一段自由文本。系统不会试图完整执行一整个科研任务；这既不可能，也没必要。系统实际做的是把需求中决定数据产品形态的信息提炼为十项明确的选择，例如交付哪类数据、表中一行代表什么、数据从哪些库取得、冲突按什么规则取舍（表~\ref{tab:spec-choices}），在实现中对应数据集执行规格这一结构。

明确这十项之后，同一份需求的执行就可以逐项核对和事后审计，不会因表述含糊而无法追因。可复现性的边界需要区分两层：规格确定之后，Core 层的解析、规范化与发布是确定性可复现的；但规格本身由模型生成，Agent 层的检索与纳入决策会随模型档位和采样变化——第\ref{ch:experiments}章样例1 在 flash 与 max 档下纳入的研究集合不同，即是一例。

相应地，系统交付的也不是一张孤立的数据表。合格的候选结果必须同时包含六类信息：数据本身、表结构、溯源信息、审计记录、验证结果、文件清单。候选结果只有通过全部质量检查后，系统才会生成正式发布版。正式发布只新增版本、不覆盖既有发布；读取时，系统依据发布清单重新校验文件摘要，发现文件缺失、损坏或与清单记录不一致即拒绝展示。

\section{主要贡献与核心机制}\label{sec:contributions}

本文将实际完成的功能归纳为三个相互关联的系统贡献。它们都建立在同一机制之上：从来源字节到发布物逐文件计算SHA-256，并在读取时重新校验，利用哈希的唯一性形成贯穿八阶段流水线的证据链。

\textbf{可验证产物与完成性绑定。}主流 Agent 框架（例如第二章所述 LangChain、AutoGen）判定任务完成的依据是三种信号：模型自报完成、对话结束、工具返回值。这三种信号都不要求系统生成可重验的产物，也不把“产物哈希重验通过”列为正式完成的必要条件。换言之，模型说完成就算完成，即便产出是空壳或伪造。本系统则把正式完成定义为唯一可达的不可变发布物。完成规则写入系统提示，运行时逐回合注入实际进度（“尚无正式发布物”“仍有工具在执行”），终态一律拿不准就拒绝。这是对“执行幻觉”的结构性约束：自然语言完成声明不能替代正式终态与可重验产物。

\textbf{运行时表结构的准入控制。}声明式LLM数据管线允许模型生成新的算子和表结构，但这些生成物进入最终产物前通常没有信任边界，生成即接受，接受即写入。本系统允许未注册的多表结构“申请进入”，但申请必须通过三项准入检查。首先是输入角色明确，哪些字段来自原始数据、哪些来自变换必须声明清楚；其次是可物化性验证，结构能否在隔离区实际执行并产生输出；最后是输出精确完整，输出列与声明列逐一对应，无遗漏无冗余。候选字节在隔离区逐文件重算摘要，变换方在代码级无法选择校验、评估与发布模块，因此开放输入不会扩大写入权限。

\textbf{证据绑定的人工确认机制。}工作流引擎的人工任务节点通常这样设计：系统发出审批请求，人工响应同意或拒绝，系统根据响应继续或中止。问题在于，响应不绑定证据摘要，系统无法验证“人工看到的内容”与“系统准备提交的内容”是否一致。本系统的审批请求携带覆盖其对象的证据摘要（例如待发布文件的 SHA-256 清单），如果人工响应晚于请求、或对象在响应前已被修改，系统拒绝恢复，要求重新审批。需要发布验收的场景（动态发布、图表证据、浏览器证据接受）不可绕过，必须经过人工确认。修正通过版本替代关系形成新版本，而不是覆盖旧产物，保留完整的版本历史。

上述三项贡献建立在\textbf{统一的证据链机制}上。来源文件进入系统时计算 SHA-256 摘要，解析后生成解析记录并再次计算摘要，规范化后生成规范化记录并再次计算摘要，依次经过兼容性检查、整合审计、校验报告，最终形成发布清单，每个环节都留下可重验的摘要。读取时重新计算摘要，不匹配即拒绝展示。这条链路使未经声明门禁或摘要不一致的候选不能进入正式数据，并保存 Agent 决策与正式产物之间的可审计关系；摘要一致本身不等于科学正确，仍需来源级和任务级核验。
