\section{真实科研中数据查找与整合的具体不足}

在生物医学研究中，“找到数据”不等于找到一个网页链接。一个可用于下游分析的数据集至少要说明六件事：它对应哪些实体和样本，来自哪个版本，原文件如何转换为当前字段，不同来源能否在同一粒度上合并，哪些值存在冲突，以及哪些判断仍需研究者确认。现有工作流程主要存在以下不足。

第一，数据来源分散且检索接口异构。同一研究问题可能同时涉及 PubMed 或 Europe PMC 中的论文、GEO/\allowbreak{}GDC/\allowbreak{}Xena 中的表达数据、ClinVar/\allowbreak{}GWAS Catalog 中的变异证据、PDB/\allowbreak{}UniProt 中的蛋白信息，以及论文附件或网页下载。不同平台的查询语言、分页方式、访问限制、版本标识和返回格式不同。研究者往往能找到“相关页面”，但难以证明是否覆盖了应查来源、是否遍历了分页、是否遗漏补充材料。

第二，可读信息不等于可计算数据。论文中的 HTML、XML、PDF 表格、扫描图、折线图和补充 XLSX 需要不同解析方法。复杂表格还可能包含合并单元格、跨页表头、脚注、单位信息和缩写。视觉模型可以读取图表，但模型输出本身具有非确定性，若不保留页码、边界框、模型身份、提示版本和置信度，就难以复核。

第三，多源数据的语义不自动一致。相同列名可能代表不同测量语义，不同列名也可能代表同一概念；基因、探针、变异、化合物和样本各自有不同标识体系。以表达数据为例，probe-level 与 gene-level 具有不同的行粒度，原始强度、归一化表达量和对数值不能仅凭列名直接拼接。以生物活性数据为例，同一化合物在不同数据库中的身份标识、实验类型和活性单位需要显式交叉映射，冲突要显式记录。

第四，人工复制整理难以复现。常见流程是在浏览器、Excel、脚本和聊天窗口间复制内容。即使最终得到 CSV，也常缺少原始文件摘要、检索条件、字段映射、被拒绝行、冲突处理和处理程序版本。后续发现错误时，研究者难以判断应修改哪一步，只能重新整理。

第五，一次性问答无法承担长流程状态。科学数据任务可能因下载、权限、人工确认或服务故障跨越多个会话。普通问答把中间状态留在上下文窗口中，一旦超时或重启，模型容易重复下载、改变处理方式或遗忘用户指令。

\section{相关工作与差异定位}\label{sec:related}

先回顾四类直接相关的工作。第一类是检索：PubMed、Europe PMC 等文献平台，以及 GEO、GDC、PDB、UniProt、ClinVar、ChEMBL 等专业数据库，提供标识稳定、字段规范的入口。但跨库研究仍需要手工组合查询条件并下载文件。通用网页搜索可以发现 API 未覆盖的页面和附件，却不能保证搜索排名反映数据质量；网页内容本身也不能直接作为证据。

第二类是解析：规则解析器处理固定格式时更容易复现，但难以覆盖布局复杂的非结构化内容。OCR 与支持视觉的大语言模型更加泛用，但识别精度仍有限。第三类是整合与溯源：传统抽取—转换—加载（Extract-Transform-Load, ETL）擅长映射固定的输入和输出结构，但难以处理运行时才确定的开放来源集合——例如任务执行到一半发现需补充某篇论文的附件数据，固定管线必须修改代码后重排重跑。第四类是 LLM 辅助：检索增强生成、工具调用和 ReAct 等方法使模型能够在回答前搜索外部信息并调用工具；然而，若直接让模型生成或改写正式数据，仍会面临幻觉、不可重复和长流程状态脆弱等问题。

综合来看，本系统采用的是一种编译器式的受控数据构建流程：自然语言研究需求是输入，具有表结构、来源、质量记录和发布回执的数据产品是输出。模型负责需求理解、来源探索和规格选择等开放式语义工作；Dataset Core 独占正式数据变换与发布权，并用强约束的证据闭环贯穿数据生命周期。研究者因此可以追问：数据从哪里来，如何变成当前形式，哪些地方仍然不确定。

\section{本系统希望解决的问题}

BioMed-QAgent 的目的不是“替研究者得出科学结论”，而是完成赛题明确提出、位置更上游的一步：将自然语言研究目标转换为结构化科学数据产品。该产品可以继续用于分析，能够追溯来源、检查质量，并可根据反馈修正。

系统试图解决四个连续问题。它们共同覆盖“Agent 外部工作 → Dataset Core 确定性流水线”的主链路：
\begin{enumerate}
  \item 根据研究目标定位合适的论文、数据库、附件、表格或图像数据（Agent 侧的需求编译与来源发现）；
  \item 把异构载体解析为明确表结构和行粒度下的规范记录（Core 的解析、规范化阶段）；
  \item 在不掩盖缺失、重复、单位差异和身份冲突的前提下完成多源整合（Core 的兼容、整合、派生阶段）；
  \item 将每一步的来源、输入摘要、处理版本、质量判断和人工修正一起发布，使结果能被验证和复用（Core 的校验、发布阶段与可持久化的人工确认）。
\end{enumerate}
系统有意不把科研分析和结论生成纳入正式完成标准。这样既符合赛题 1A 的任务边界，也避免将“数据是否正确”与“模型解释是否听起来合理”混在一起。相应地，系统的工程投入集中在赛题要求的核心链路——来源发现与覆盖、异构解析、清洗整合、图表提取与全链路溯源——其逐维度实证与边界见第五章。

\section{研究问题与数据需求}

本文要解决的核心问题是：用户以自然语言提出的研究需求，能否被系统可靠地转换为定义明确、过程可控且结果可复核的数据交付？回答这一问题，需要先明确两件事：系统应从需求中提取并固定哪些关键信息，以及合格结果必须满足哪些条件。

用户最初输入的是一段自由文本，其中可能包含多种解读。系统不试图穷尽地形式化全部科学意图；这种做法既不可能，也没有必要。系统只固定那些“一旦改变，数据产品的含义就会随之变化”的关键选择。这些选择共有十项，共同构成本次执行的数据集规格；在实现中对应数据集执行规格（DatasetExecutionSpec）结构：

明确这十项之后，同一份需求就可以被反复执行、逐项核对和事后审计，不会因表述含糊而产生不同的结果。

相应地，系统交付的也不是一张孤立的数据表。合格的候选结果必须同时包含六类信息：
\begin{itemize}
  \item 数据本身：可以是单张表，也可以是由主外键关联的多张表组成的集合；
  \item 表结构：各表的字段结构与约束；
  \item 溯源信息：数据来自哪些来源，每条记录在原始数据中如何定位；
  \item 审计记录：完整保留处理过程中被丢弃的数据、检测到的冲突以及所做的修正；
  \item 验证结果：各项质量门的判定结论；
  \item 文件清单：逐一登记正式交付的文件及对应的 SHA-256 校验值。
\end{itemize}
候选结果只有通过全部质量门检查后，系统才会生成正式发布版。正式发布只新增版本、不覆盖既有发布；读取时，系统依据发布清单重新校验文件摘要，发现文件缺失、损坏或与清单记录不一致即拒绝展示。这里的“不可变”不表示能够防止同一 OS 账户完全重写文件系统，也不提供密码学防篡改能力。这样设计是为了让使用者既能直接基于表格开展分析，也能逐项查证数据来源和处理过程，从而使交付物可追溯、可复现。

\section{主要贡献与设计要点}\label{sec:contributions}

本文将实际完成的功能归纳为三个相互关联的系统贡献。它们都建立在同一机制之上：从来源字节到发布物逐文件计算 SHA-256，并在读取时重新校验，形成贯穿第四章八阶段流水线的证据链。下文分别说明每项贡献所针对的实际缺口。

贡献一：将任务完成绑定到唯一可验证的产物，而不是模型自报。主流 Agent 框架（LangGraph、AutoGen、OpenAI Agents 等）以模型自报、对话结束或工具返回值界定“完成”，不设“产物哈希重验失败即拒绝展示”的正式门\cite{langgraph,autogen,openai-agents}。本系统把正式完成定义为唯一可达的不可变发布物；普通 Run 仍可在无发布物时结束，运行结束时的统一发布门仍属待办，当前依靠提示词、状态分层与 supervisor 约束。

完成契约写入系统提示，运行时逐回合注入“尚无正式发布物”“仍有工具在执行”等进度真相，终态一律拿不准就拒绝（fail closed）。这是对“执行幻觉”（自报完成、产出为空壳或伪造行）的结构性对策——对抗验证中 qwen3.7-plus 曾三轮谎报完成，占位符空壳是内容筛查落地前的唯一穿透、此后未再发生（机制见 \ref{sec:three-layer} 节）。

贡献二：表结构可以在运行时申请进入，但准入权始终在 Core。声明式 LLM 数据管线（DocETL、Palimpzest）中，LLM 生成的算子与表结构在进入最终产物前没有信任边界，其校验停留在准确度层面，最终输出也只是普通文件\cite{docetl,palimpzest}。本系统允许未注册的多表拓扑“申请进入”，但须通过限定准入检查（输入角色、可物化性、输出精确闭合）。候选字节在隔离区逐文件重算摘要，且变换方在代码级无法选择校验、评估与发布模块。因此，开放输入不会扩大写入权限（实证见 gold7 预检 11 次结构化拒绝后的正式闭环；机制见第四章 B 路线）。

贡献三：将人工确认与证据绑定，支持恢复，并保留版本历史。工作流引擎（Temporal、Airflow）的人工任务节点不绑定证据摘要，Temporal 官方文档亦提示开发者自行校验审批数据\cite{temporal-approval}。

本系统的审批请求携带覆盖其对象的证据摘要；如果响应与任务身份不符，系统就拒绝恢复。动态发布、图表证据、浏览器证据接受等需要发布验收的场景不可绕过，且强制人工确认。修正通过 supersedes 关系形成新版本，而不是覆盖旧产物（详见 \ref{sec:hil} 节）。
