# 重新调研审查结论

## 一、总判断

新的四步工作流**方向正确，且与赛题目标和原架构理念总体契合**，但目前提案中有一个关键边界必须修正：

> 应设计为“Agent 编排、Pipeline 确定性处理与验证、统一发布”，而不是“Pipeline 先生成 CSV，LLM 再自行补数据并直接合并 CSV”。

建议结论：

| 评估项 | 结论 |
|---|---|
| 业务必要性 | 高 |
| 与赛题契合度 | 高 |
| 与原架构理念契合度 | 中高，但需明确边界 |
| 当前代码直接支持程度 | 中低 |
| 是否值得实施 | 值得 |
| 是否应一次性全部实现 | 不建议 |
| 首要阻塞 | GEO live 表达数据闭环、Agent 数据持久化、确定性合并契约 |

原设计的核心不是“Pipeline 必须自主搜索”，而是：

- Agent 理解问题、选择能力和数据来源；
- Pipeline 强制执行数据处理阶段；
- 只有通过 Validation Gate 的结果才能作为正式 Artifact；
- Agent 不能直接拼装最终 CSV。

这些原则在 [ARCHITECTURE.md](file:///d:/Code/BioMedQAgent/docs/ARCHITECTURE.md#L19-L67) 和 [backend-data-closure-design.md](file:///d:/Code/BioMedQAgent/docs/superpowers/specs/2026-07-12-backend-data-closure-design.md#L49-L113) 中已经明确。因此，新流程可以改变“谁负责发现和编排”，但不能削弱 Pipeline 的验证和发布责任。

# 二、对四个步骤逐项审查

## 1. LLM 分析问题并进行初步调研

### 结论：合理、必要，当前已经具备基础

当前 Agent 已承担：

- 理解研究主题；
- 选择数据库；
- 生成查询；
- 搜索 PubMed、GEO 等来源；
- 识别 PMID、GSE 等 accession；
- 调用下载工具；
- 最终调用 Pipeline。

对应实现见 [agent.py](file:///d:/Code/BioMedQAgent/backend/app/agent_loop/agent.py#L35-L50)。

这一步符合原始设计中的 Agent 职责：

> Agent 负责理解问题、生成查询、选择数据源和生成结构化任务描述；不直接生成最终 CSV。

### 需要补充的约束

LLM 初步调研的结果不能只停留在对话上下文中。至少应将以下内容变成任务级、可追溯的结构化记录：

- 查询语句；
- 查询来源；
- 查询结果状态；
- PMID/GSE/project ID 等候选标识；
- Agent 的选择理由；
- 被排除的候选及原因；
- 证据链接或来源关系。

当前 `RunContext.query_log` 能记录检索清单，但其主要是运行时内存状态；当前任务目录也没有正式的 `agent_results/` 结构。TODO 已指出这一缺口：[TODO.md](file:///d:/Code/BioMedQAgent/docs/TODO.md#L77-L84)。

因此，步骤 1 的正确定位应是：

> LLM 负责“候选发现与计划形成”，不是负责产生可信的最终数据行。

## 2. Pipeline 接收少量参数，完成第一轮工作流并生成 CSV

### 结论：方向合理，但“少量参数”必须是结构化任务意图，而不是过度简化为三个字符串

当前 Pipeline Tool 的参数是：

```text
topic
databases
pmid
gse
mode
```

见 [pipeline/tool.py](file:///d:/Code/BioMedQAgent/backend/app/pipeline/tool.py#L127-L134)。

当前实现中：

- `pmid` / `gse` 可以约束 Discovery；
- Pipeline 仍会自主完成 Discovery → Acquisition → Processing → Artifact Build → Validation；
- 只有验证成功后才发布 Artifact；
- Agent 不直接写最终 CSV。

这与“少传参、保留 Pipeline 自主性”的目标基本一致。

但当前 Pipeline 的真实能力仍然具有明显范围限制：

- Processing 当前主要围绕 GEO tximport；
- `_execute_stage()` 对 Processing 直接使用 `acquisition.source_assets[0]`；
- Artifact Build 也主要围绕单个 ParsedDataset；
- 多源字段对齐和合并仍未形成完整闭环。

对应代码见 [runner.py](file:///d:/Code/BioMedQAgent/backend/app/pipeline/runner.py#L840-L887) 和 [processing.py](file:///d:/Code/BioMedQAgent/backend/app/pipeline/stages/processing.py#L352-L374)。

因此，“少量参数”可以保留，但内部契约必须逐步升级为：

```text
TaskSpecification
    ├── topic
    ├── queries
    ├── dataset selections
    ├── requested outputs
    └── optional execution hints
```

而不是长期依赖 `pmid`、`gse` 两个特例参数。

### 对第一轮 CSV 的判断

第一轮 CSV 可以作为：

- 初步结果；
- 可验证结果；
- 后续 Agent 调研的依据；
- 后续合并的一个输入版本。

但不能被当成“最终结果”的同义词。必须明确它的状态，例如：

```text
validated_intermediate
```

并保留：

- `run_id`；
- 输入参数摘要；
- 来源清单；
- 数据版本；
- 验证报告；
- 未解决警告；
- 缺失字段；
- 下一轮是否仍有补充空间。

否则后续第二轮补充会难以判断是新增数据、重复数据还是覆盖数据。

## 2.1 Pipeline 失败后完整重跑或局部重跑

### 结论：完整重跑可行；局部重跑需要严格定义，不能直接开放任意 stage skip

当前 Runner 已经具备部分恢复能力：

- StageAttempt；
- 输入摘要；
- 参数摘要；
- 输出摘要；
- 成功阶段输出持久化；
- digest 匹配后的阶段复用；
- 失败后从已验证阶段继续。

见 [runner.py](file:///d:/Code/BioMedQAgent/backend/app/pipeline/runner.py#L566-L675) 和 [state.py](file:///d:/Code/BioMedQAgent/backend/app/pipeline/state.py#L153-L226)。

当前输入摘要按上游阶段摘要计算，参数摘要包含 topic、mode、fixture 内容等，见 [runner.py](file:///d:/Code/BioMedQAgent/backend/app/pipeline/runner.py#L1040-L1075)。

### 完整重跑

完整重跑是可行的，且风险较低，前提是：

1. 每次重跑产生新的 `run_id`；
2. 不覆盖旧版 Artifact；
3. 输入参数和来源集合进入新的 digest；
4. 新旧 Manifest 都保留；
5. 只有新版本通过 Validation Gate 后才能成为当前发布版本；
6. 旧版本仍可回溯和下载。

当前运行时已经支持同一 Task 的多次用户 Run，但一个 Task 同时只能有一个非终态 Run，见 [runtime.py](file:///d:/Code/BioMedQAgent/backend/app/domain/contracts/runtime.py#L63-L68) 以及 [manager.py](file:///d:/Code/BioMedQAgent/backend/app/runtime/manager.py#L1167-L1225)。

所以合理语义是：

```text
同一 Task
  Run 1：初步 Pipeline
  Run 2：带新增 PMID/GSE 或新参数的完整重跑
  Run 3：补充数据后的重新构建
```

而不是在同一 Agent Run 内任意多次调用并修改同一个发布槽位。

### 当前实现的重复调用限制

当前 `run_research_pipeline` 会在同一个 `RunContext` 中预留一次 Pipeline publication slot；再次调用会返回 `already_run`，见 [pipeline/tool.py](file:///d:/Code/BioMedQAgent/backend/app/pipeline/tool.py#L139-L156)。

这项限制对“一个 Agent Run 只产生一个正式 Pipeline 发布结果”是合理的，但不应该被解释为“一个 Task 永远只能运行一次”。

正确区分：

| 场景 | 是否应支持 |
|---|---|
| 同一 Agent Run 内重复调用同一 Pipeline | 默认不支持 |
| 新用户输入触发新的 Agent Run | 支持 |
| 新 Run 使用不同 accession 或参数重新执行 | 支持 |
| 新 Run 复用已验证阶段结果 | 支持 |
| 新 Run 覆盖旧 Artifact | 不支持 |
| 任意跳过上游阶段直接执行下游阶段 | 不支持 |

### 局部重跑

局部重跑不是简单增加 `start_from="processing"`。

Pipeline 阶段存在依赖关系：

```text
Discovery
   ↓
Acquisition
   ↓
Processing
   ↓
Artifact Build
   ↓
Validation
```

因此局部重跑必须计算依赖闭包：

| 变化类型 | 最早需要重跑的阶段 |
|---|---|
| topic / query / accession 变化 | Discovery |
| 下载 URL、下载策略变化 | Acquisition |
| parser、字段映射、清洗规则变化 | Processing |
| 输出格式变化 | Artifact Build |
| 仅验证规则变化 | Validation |
| 新增 Agent 数据源 | 至少 Discovery/Acquisition/Processing，通常还包括 Artifact Build |

例如，不能只重新运行 Processing，却继续使用与旧 Processing 输入不匹配的 Artifact Build 输出。

因此局部重跑应定义为：

```text
requested_stage
    -> dependency closure
    -> new StageAttempt chain
    -> new artifact version
    -> Validation Gate
```

而不是提供一个让 Agent 任意传 `skip_stages` 的自由接口。

## 3. Pipeline 无法产生新进展后，LLM 进行其它检索和数据补充

### 结论：业务上必要，且符合赛题“人机协同迭代”，但“不会产生新进展”不能由 LLM 主观决定

这一阶段实际上是新工作流最有价值的部分。

赛题明确要求：

- 发现错误或反馈后能够修正；
- 支持多源异构数据；
- 支持正文、表格、附件、图像等数据获取；
- 保留来源和处理记录。

见 [PROBLEM.md](file:///d:/Code/BioMedQAgent/PROBLEM.md#L22-L32) 和 [PROBLEM.md](file:///d:/Code/BioMedQAgent/PROBLEM.md#L55-L69)。

当前系统也已经具备 Agent-only 能力，例如：

- 浏览器视觉采集；
- PDF 和补充材料获取；
- 图表数据提取；
- GDC、Xena、Reactome、PubChem、PDB 等工具层能力。

但这些数据如果只存在于 LLM 对话或临时文件中，就无法满足最终 CSV 的可追溯性要求。

### 必须区分三类 Agent 补充结果

#### A. 仅作为研究线索

例如：

- “可能还有一个相关 GEO 数据集”；
- “论文中提到某个补充表格”；
- “页面上看起来存在某个样本”。

这类内容可以保留在 Agent 调研记录中，但不能进入最终主数据。

#### B. 已获取但尚未标准化的数据

例如：

- 下载的 JSON、TSV、PDF、PNG；
- 浏览器截图；
- 图表提取结果；
- 外部 API 返回的原始响应。

这类内容应进入：

```text
source_assets/
download_log/
agent acquisition records
```

并形成正式的 `SourceAsset`，包括 checksum、来源 URL、下载尝试和媒体类型。

#### C. 可以纳入最终数据的结构化结果

这类结果必须经过：

```text
SourceRecord
    -> SourceAsset
    -> ParsedDataset
    -> cleaning / alignment
    -> Artifact Build
    -> Validation Gate
```

不能让 Agent 直接把一段 JSON 或一张 CSV 拼入 `main_data.csv`。

### “无新进展”建议使用结构化判定

可以让 Agent 做最终策略判断，但系统应提供证据指标：

- 当前查询是否产生新来源；
- 是否新增 accession；
- 是否新增 SourceAsset；
- 是否新增有效记录；
- 新增记录是否通过 schema 校验；
- 数据质量指标是否改善；
- 失败是否属于可重试错误；
- 当前缺口是否已经无法由当前数据库和工具补齐。

因此应记录类似：

```text
progress_decision:
  new_sources: 0
  new_assets: 0
  new_records: 0
  quality_delta: 0
  unresolved_requirements: [...]
  decision: switch_to_agent_supplement
  reason: structured evidence
```

LLM 可以解释这个决策，但不应单独成为唯一证据。

## 4. 合并第一轮 CSV 和第二轮 Agent 数据，产生最终 CSV

### 结论：必要，但不能由 LLM 直接完成；必须新增“确定性合并与最终验证层”

这是当前提案中风险最高的一步。

原设计规定：

> Agent 不直接拼装最终 CSV，Pipeline 负责字段对齐、追溯、验证和发布。

因此，“合并”应该理解为：

```text
Pipeline validated intermediate artifacts
                 +
Agent-acquired source assets / parsed datasets
                 ↓
Deterministic merge and alignment
                 ↓
Final Artifact Build
                 ↓
Validation Gate
                 ↓
published final artifacts
```

而不是：

```text
LLM 读取第一轮 CSV
    +
LLM 自己获取几条数据
    +
LLM 直接写 final.csv
```

### 合并必须解决的技术问题

#### 1. 行粒度

`main_data.csv` 只能包含一种行粒度，当前架构对此有明确规定，见 [ARCHITECTURE.md](file:///d:/Code/BioMedQAgent/docs/ARCHITECTURE.md#L386-L399)。

因此合并前必须明确：

- 基因 × 样本；
- 样本元数据；
- 文献记录；
- 通路成员；
- 图表数据点；

这些不能不加区分地放入同一个 CSV。

#### 2. 主键与去重

必须定义：

- `record_id`；
- `dataset_id`；
- `source_id`；
- `asset_id`；
- `sample_id`；
- Agent 数据与 Pipeline 数据的冲突处理规则。

不能用“最后一次写入覆盖前一次”的方式解决冲突。

#### 3. 字段对齐

当前 Pipeline 已有字段对齐基础，但多源合并仍未完整接入，见 [processing.py](file:///d:/Code/BioMedQAgent/backend/app/pipeline/stages/processing.py#L251-L320) 和 TODO [§1.2](file:///d:/Code/BioMedQAgent/docs/TODO.md#L20-L24)。

需要明确：

- 原始字段名；
- 标准字段名；
- 映射规则；
- 单位转换；
- 缺失值语义；
- 类型转换；
- 冲突字段保留策略。

#### 4. 来源追溯

每一行新增数据都必须有：

- `source_id`；
- `asset_id`；
- 原始文件；
- 原始行号；
- 原始列名；
- 原始值；
- 处理步骤。

否则第二轮数据会成为不可审计的数据孤岛。

#### 5. 合并失败

部分数据不能合并时，不应静默丢弃，也不应自动强行转换。应产生：

- warning；
- merge rejection；
- unmapped records；
- conflicts；
- quality report。

最终是否发布仍由 Validation Gate 决定。

# 三、与原设计理念的契合程度

## 契合部分

### 1. Agent-as-orchestrator

新流程让 Agent：

- 先理解问题；
- 先做广泛检索；
- 再决定是否调用 Pipeline；
- 根据 Pipeline 结果继续补充；
- 最后触发新一轮确定性处理。

这比当前“Agent 检索后调用一次 Pipeline，然后结束”的流程更符合人机协同理念。

### 2. Pipeline 仍然保留确定性价值

只要 Pipeline 继续负责：

- 下载校验；
- 解析；
- 清洗；
- 字段对齐；
- 来源追溯；
- Artifact Build；
- Validation Gate；

新工作流并没有削弱 Pipeline，反而提升了它的定位：

> Pipeline 不再是唯一的数据发现者，而是所有正式数据进入交付包前的可信处理边界。

### 3. 更符合赛题要求

赛题考察的不只是单次成功生成 CSV，还包括：

- 多源数据处理；
- 数据质量控制；
- 来源追溯；
- 发现错误后的修正；
- 人机协同迭代。

新流程对这些要求的覆盖明显优于原来的单次 Pipeline 调用。

## 不契合部分

### 1. “LLM 自主获取的数据”不能天然等于可信数据

LLM 获取的数据可能来自：

- 非结构化网页；
- 页面截图；
- PDF；
- 图表识别；
- 手工推断；
- 不稳定 API。

如果这些数据绕过统一 SourceAsset、ParsedDataset 和 Validation Gate，就会违反原设计的核心原则。

### 2. “最终合并”不能由 LLM 实现

LLM 可以：

- 选择数据；
- 解释冲突；
- 提供映射建议；
- 请求用户确认。

但不能直接承担：

- 主键生成；
- 去重；
- 类型转换；
- 单位换算；
- 逐行来源绑定；
- 最终发布。

### 3. Pipeline 的自主性不能成为弱契约的理由

“少传参”可以保留，但 Pipeline 内部仍应接收完整、可版本化的 `TaskSpecification`。否则后续重跑无法判断：

- 为什么本次结果不同；
- 哪些参数变化导致了变化；
- 哪些阶段可以安全复用；
- 新旧 Artifact 是否可比较。

# 四、推荐的目标工作流

建议将提案重新表述为：

```text
1. Agent 初步分析与检索
   └─ 生成可持久化的 ResearchPlan / TaskSpecification

2. Agent 调用 Pipeline
   └─ 传入少量高价值参数
   └─ Pipeline 自主完成发现、获取、处理、验证
   └─ 生成 validated intermediate artifact version

3. Agent 评估 Pipeline 输出
   ├─ 若存在可修复失败：提交新 Run 完整重跑或受控局部重跑
   ├─ 若有明确数据缺口：调用其它检索/浏览器/PDF/数据库工具
   └─ 若没有新增证据：结束补充阶段

4. Agent 补充数据进入统一数据边界
   └─ SourceRecord
   └─ SourceAsset
   └─ ParsedDataset
   └─ cleaning / alignment

5. Pipeline 重新构建最终版本
   └─ 合并 Pipeline 数据与 Agent 数据
   └─ Validation Gate
   └─ 发布 final artifact version
```

核心变化是：

> 第二轮不是“LLM 直接补 CSV”，而是“LLM 补充数据源，Pipeline 重新构建最终 CSV”。

# 六、必须锁定的架构不变量

建议后续设计和测试至少固定以下规则：

| 不变量 | 验收要求 |
|---|---|
| Pipeline 是唯一正式发布者 | Agent 不能直接生成或替换最终 Artifact |
| 每次重跑有独立版本 | 不覆盖历史 Manifest 和 Artifact |
| 参数变化影响版本身份 | topic、来源、解析器、映射规则变化必须进入 digest |
| 局部重跑遵循依赖闭包 | 不允许产生上游输入不匹配的下游结果 |
| Agent 数据可追溯 | 每条进入最终数据的记录都关联 SourceRecord/Asset/Locator |
| 合并可重复 | 同一输入版本重复合并得到相同内容和 checksum |
| 合并冲突显式化 | 冲突写入 warning/quality report，不静默覆盖 |
| 无新进展可解释 | 停止补充必须有结构化证据 |
| 失败不可伪装成功 | 失败、部分成功、未验证结果不能进入正式 Artifact |
| 第一轮结果可区分 | `intermediate` 与 `final` 不能只靠文件名区分 |

# 最终建议

**批准这个新工作流作为目标方向，但不批准按当前文字直接实现。**

需要将其修正为：

> Agent 负责初步调研、迭代决策和补充数据源；Pipeline 负责所有结构化数据的确定性处理、合并、验证和最终发布。反复调用通过新的 durable Run 实现，局部重跑遵循依赖闭包，Agent 补充数据必须进入统一来源和处理契约。

这样既保留 Pipeline 的必要性，也解决了当前“Pipeline 自主发现能力有限、Agent 数据无法进入 CSV”的结构性问题，同时不会破坏原设计最重要的可信性和可追溯性。
