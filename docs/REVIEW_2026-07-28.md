## 1. 数据流架构调研

### 调研范围
完整追踪了 LLM 工具 → Pipeline → CSV 的数据流。

### 关键发现

**Pipeline 与 LLM 工具完全解耦**：
- Pipeline 自主执行 Discovery → Acquisition → Processing → Artifact → Validation
- 不消费 LLM 工具返回的任何结构化数据
- 唯一桥接点是 `run_research_pipeline(topic, pmid, gse)` 的 3 个字符串参数

**LLM 工具输出不持久化**：
- 搜索结果、通路分析等仅在 Agent 对话上下文中（内存）
- 不在任务目录中留下任何痕迹
- 对话压缩后即丢失

**数据孤岛**：
```
Agent 工具 → 对话上下文（内存，会丢失）
Pipeline  → artifacts/（磁盘，持久化）

两者互不相通，形成两个独立数据岛
```

**main_data.csv 在 live 模式下无表达数据**：
- Processing 在 live 模式下跳过 tximport 解析（缺少 SOFT 文件）
- 只产出 `measurement_type="sample_metadata"` 的空行
- expression_value = NULL

详细报告见对话中的调研输出。

## 3. Pipeline 设计必要性评估

### 规模
Pipeline 共 5,459 行代码，分布在 13 个文件中。

### 核心价值
| 模块 | 必要性 | 理由 |
|------|--------|------|
| Discovery | ⚠️ 可降级 | 应改为接收 Agent 传入的 SourceRecord，而非自己调 NCBI |
| Acquisition | ⚠️ 需重构 | 只支持 NCBI FTP，应改为通用协议 |
| Processing | ⚠️ 需修复 | live 模式产出空数据是 bug |
| Artifact Build | ✓ 核心 | 13 CSV 格式 + lineage 溯源是赛题加分项 |
| Validation | ✓ 核心 | source_value_lineage 逐行校验是差异化能力 |
| Runner | ⚠️ 可精简 | 基础设施可保留，stage 编排可简化 |
| State | ✓ 必要 | 轻量状态管理合理 |
| Tool | ✓ 必要 | Agent ↔ Pipeline 桥接点 |

### 核心矛盾
Pipeline 被设计为**自主型**数据获取系统（自己搜 NCBI），但 Agent 才是天然的**数据查找者**（拥有 15+ 工具）。两者功能重复，且 Pipeline 的 Discovery/Acquisition 远不如 Agent 灵活。

### 建议方向
Pipeline 从"自主型"转型为"服务型"：接收 Agent 传入的数据源引用 → 处理 + 溯源 + 验证 → 产出 CSV。

## 4. 新工作流设计评审

### 提案

```
1. LLM 分析问题 + 初步调研
2. Pipeline 变成 Agent 可反复调用的工具
   2.1 失败后可完整或局部重跑
3. LLM 自主补充数据（浏览器、手动检索等）
4. 合并 Pipeline CSV + LLM 工具数据 → 最终 CSV
```

### 逐步骤可行性

| 步骤 | 可行性 | 阻塞点 |
|------|--------|--------|
| 1. LLM 调研 | ✅ 已就绪 | 无 |
| 2. 多次调用 | ⚠️ | `reserve_pipeline_publication()` 单次限制；~50 行可解 |
| 2.1 局部重跑 | ❌ | 需 ~200 行新原语（start_from, stage skip）；建议 P2 |
| 3. LLM 补数据 | ✅ 已就绪 | 无 |
| 4. 数据合并 | ❌ | 需 ~300 行新基础设施（agent_results/ + merge 逻辑）；建议 P1 |

### 设计合理性
**方向正确**：Agent-as-orchestrator 与赛题的"人机协同迭代"理念一致，与现有双层架构兼容。

**核心矛盾**：Pipeline 当前是"自主型"，新工作流要求"服务型"。这是方向性转变，不是实现细节。

### 建议路径
```
Phase A (P0, ~50行): 解除单次调用限制
  → artifacts/{run_id}/ 隔离目录

Phase B (P1, ~200行): 完整重跑闭环
  → 不同参数 = 不同 digest = fresh run
  → 同一 Run 内多次调用
  
Phase C (P2, ~300行): 数据合并
  → agent_results/ + merge 逻辑

Phase D (P2, ~200行): 局部重跑
  → start_from 参数
```

## 6. 2026-07-31 托管子 Agent 采集边界复核

本轮补齐了托管 child Run 的生产路径：GDC、PDB、Xena 的 API/下载请求在
RunContext 已绑定 crawler 时统一经过 lifespan-owned `CrawlerFacade`；PDB 的
JSON POST 使用 pinned `api_request`，Xena 的 S3 XML listing 保留分页解析。没有
绑定 facade 的隔离 fixture context 才允许继续使用旧 `urllib` helper。

child 的 browser、visual capture、GEO、GDC、PDB、Xena 下载都使用同一个
`staging/subagents/<subagent_id>` 边界，SourceAsset 经过 checksum/metadata 校验
后原子提交到任务 `source_assets/`，并通过 `SubagentResult.source_asset_ids`
返回轻量引用。正式 Pipeline artifact 发布边界未改变。

剩余限制：主 Agent 直接调用 GDC/PDB/Xena 时仍保留兼容性的 task raw 文件响应，
只有 child 下载路径会生成并返回 SourceAsset 元数据；后续若要统一主 Agent 路径，
应迁移到同一 SourceAsset acquisition contract，而不是恢复各技能的私有 HTTP 客户端。
