**定量流行病学（Agent 缺失）**

## 4. 问题②：no_data 归因核查（数据源 vs 工具）

### 4.1 事实核查（本机实测 + NCBI 原始核对）

| accession | 下载的 series matrix（实测解压） | NCBI FTP 实际文件 | 真实数据位置 |
| --- | --- | --- | --- |
| GSE173954 | 3,282 B，解压 36KB **纯 `!Series_*` 元数据，无 `!series_matrix_table_begin`** | matrix 3.2K（与下载一致，未截断）；**soft/ 15M family.soft.gz**；suppl/ 仅 RAW.tar(601M) | **soft family 含真实表达数据**（但内核无 SOFT 解析，见 §5.3） |
| GSE327021 | 3,558 B，元数据 only | matrix 3.5K；suppl/ 含 `GSE327021_raw_counts.txt.gz` 1.3M | **supplementary raw counts**（`supplementary_matrix` 可解析） |
| GSE266328 | 2,867 B，元数据 only | matrix 2.8K；suppl/ 含 normalized 注释计数文件 6.4M | **supplementary 归一化计数** |
| GSE160389 | 2,212 B，元数据 only | matrix 2.2K；suppl/ 仅 RAW.tar(176M) | 无现成矩阵（该系列本身数据形态受限） |

**关键事实**：
1. 下载**未截断**——本地文件字节数与 NCBI 完全一致；四个文件确实是"元数据-only 矩阵"。这是 **NCBI 侧真实行为**（RNA-seq 系列自 2021 年起矩阵文件不含数据表；个别阵列系列也出现空矩阵）。
2. 但**数据源并非无数据**：GSE327021/GSE266328 有 supplementary count 文件；GSE173954 有 15M SOFT family。工具链中 `list_geo_supplementary_files`、`download_geo(file_type='suppl')`、`geo.expression.v1(supplementary_matrix)` 路径**全部存在且已验证**，只是本轮从未走到。
3. 因此"检查数据源可用性或调整查询后重试"的推荐语是**误导性的**：数据可用，是文件选择与解析路径没接上。

### 4.2 确认的代码级缺陷（工具侧，非数据源）

1. **[P0] `search_geo` 解析崩溃**：`app/integrations/ncbi/parsers.py:153` `sample_count=int(item.get("n_samples", len(samples)))` —— 当 esummary 返回 `n_samples=""`（个别 GSE 记录无样本数）时 `int("")` 抛 `ValueError`，整个 batch 解析失败，`search_geo` 对 Agent 返回 `error: invalid literal for int() with base 10: ''`。本轮 2 次查询因此失败并触发换词重试。
2. **[P0] `download_geo` 无内容校验（fail-fast 缺失）**：`app/skills/builtin/acquisition/geo.py` `_resolve_download` 只按 URL 下载，`acquire_source` 仅校验大小/哈希，**不校验 gzip 内容是否含 `!series_matrix_table_begin`**。元数据-only 文件被报告为"下载成功"，把数据问题推迟到 parse 阶段才暴露，Agent 白跑一轮 build。
3. **[P1] `read_file_head` 不解压 gzip**：预检步骤（系统提示第 3 步要求"下载后用 read_file_head 检查表头"）对 GEO 标准 gz 格式输出二进制乱码，预检环节形同虚设。
4. **[P2] 错误信息不完整**：`download_geo` 对 `file_type="series_matrix"` 报 `unsupported file_type` 却不列出合法值（matrix/soft/suppl），浪费 Agent 一轮；`search_reactome` 的 `species` 多余属性/`term` 必填错误同理（已由 ISSUES 记录过同类问题）。

### 4.3 Agent 策略缺陷

1. **单 binding 构建**：spec 只含 `binding_geo_ad`（GSE173954 matrix）。发现列表有 40+ 个候选 GSE，vetting 过的也有多个，但构建失败后**未发起第二次构建**（下载的 GSE327021/GSE266328 从未进入 build）。
2. **过度泛化**：Agent 在文本中写道"GEO 的 RNA-seq 数据集的 series matrix 文件均仅含元数据…这是 GEO RNA-seq 数据的固有限制"——方向对，但未采取"换用 supplementary counts"这一既有能力，也未对照系统提示"microarray 优先、换数据集"的明确指引。
3. **对已知能力的遗漏**：`list_geo_supplementary_files` 只对 GSE173954 调用过一次（结果合理为 0），对存在 counts 文件的 GSE327021/GSE266328 从未调用。
4. **汇报无引用**：全文无 PMID/GSE/DOI 链接，治疗策略表无法溯源。

## 5. 问题③：改进设计建议

### 5.1 工具层（最快见效，建议 P0 优先）

| # | 建议 | 落点 |
| --- | --- | --- |
| T1 | `parse_geo_esummary` 的安全 int 解析：`n_samples` 空/非数字时回退 `len(samples)`，任一记录失败不拖垮整批 | `app/integrations/ncbi/parsers.py:153` |
| T2 | `download_geo` 下载后对 `matrix` 类型做内容预检：解压头部，检查 `!series_matrix_table_begin`；缺失时返回结构化错误 `{"reason_code":"empty_series_matrix","hint":"数据表在 soft/ 或 suppl/，建议 download_geo(file_type='soft'|'suppl')"}` 且**不落 asset 为"成功"** | `geo.py:download_geo_adapter` |
| T3 | `read_file_head` 对 `.gz/.bgz` 流式解压后再取前 N 行（不改变其它行为） | 文件读取工具 |
| T4 | `download_geo`/`search_reactome` 等 schema 错误信息列出合法取值，减少 LLM 试错轮 | 各 skill 描述/异常文案 |
| T5 | `download_geo` 增加便捷语义：`file_type="suppl"` 时若无 filename 且有且仅有一个"疑似矩阵"候选（含 count/expression/normalized 命名）则自动选用并返回文件名 | `geo.py:_resolve_download` |

### 5.2 Agent 提示层（成本最低）

| # | 建议 |
| --- | --- |
| P1 | **多 binding 兜底**：系统提示"构建失败处理"节增加——候选数据集中 ≥2 个进同一个 `execute_dataset_build` spec（同 family/granularity），单个 binding 空表不拖垮整个 build；或失败后必须换一个已下载/可下载的候选再构建一次才允许收尾 |
