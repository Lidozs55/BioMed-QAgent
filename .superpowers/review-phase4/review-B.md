| **B1** | **Critical** | `backend/app/pipeline/dataset_build_tool.py:150-158`; `backend/app/datasets/contracts.py:139-154` | `DatasetBuildSpec.build_id` and `SourceBinding.binding_id` only require non-empty strings. A tool caller can submit an absolute `build_id` (for example `/tmp/published-by-agent`) and `build_root / build_id` discards the task-local prefix, causing `datasets_build`, state, generated files, and publication output to be written outside the task work directory. Binding IDs are also interpolated into generated filenames, allowing `../` components to escape the build workspace before later relative-path checks fail. | Apply the same strict single-component ID validator used by `TaskWorkDir` to `build_id` and `binding_id`, and reject any path-like value before constructing paths. | `spec = valid_spec(build_id="/tmp/outside"); await execute_dataset_build(...); assert not (Path("/tmp/outside") / "dataset_manifest.json").exists()` (and parameterize `binding_id="../../escape"`). |
| **B2** | **Important** | `backend/app/datasets/runtime/executor.py:487-501` | V2 checkpoint reuse does not include the actual source-asset digest in the first operation's input or parameter digest. Repeating `execute_dataset_build` with the same `build_id` and path after replacing the source file reuses acquire/parse/canonicalize/integrate/validate/publish checkpoints and returns the old publication. Confirmed probe: first GDC file produced values `1.5/2/3/4.25`; after replacing it with `99/100/101/102`, the second call returned the same `publication_id` and `merged/primary.csv` still contained the old values. | Include the sorted binding-to-`SourceAsset.sha256`/size mapping in the executor input digest (or invalidate the build state when source assets change). | Call the tool twice with the same spec/build ID and source path, mutate the file between calls, then assert the second result has a different publication ID and the new value in `merged/primary.csv`. |
| **B3** | **Important** | `backend/app/datasets/build/expression_runner.py:358-364` | V2 publication flattens every manifest artifact to `staged_dir / src.name`, while `dataset_manifest.json` retains paths such as `merged/primary.csv`, `canonical/binding.csv`, and `batches/...`. The immutable publication therefore contains a manifest whose artifact references do not exist in its own publication directory; a manifest-driven consumer cannot locate the primary file. | Preserve each artifact's `relative_path` under the version directory and verify the copied file set against the manifest before rename. | Run a valid V2 build; load `publish/*/dataset_manifest.json`; for every entry assert `(publication_dir / entry["relative_path"]).is_file()`; current code fails for `merged/primary.csv`. |
| **B4** | **Important** | `backend/app/datasets/build/expression_runner.py:358-364`; `backend/app/datasets/build/invariants.py:91-117` | The V2 publication gate does not verify the manifest's artifact inventory against the bytes being promoted. `_publish` silently skips a missing artifact (`if src.is_file()`), and `check_release_invariants` only reads the first provenance artifact and compares the number of listed sources, not each declared artifact's size/hash or the exact trusted asset IDs. A file deleted or modified after profile validation can produce a passed release with a stale manifest and incomplete/tampered publication. | Before promotion, require every manifest artifact to be a regular file with exact declared size and SHA-256, and require provenance source IDs to equal the build's source-asset set. | Build through validation, delete or edit `schema.json`/`provenance.json`, invoke publish, and assert it raises `BuildError`; also replace provenance `sources` with a same-count fake asset and assert the invariant gate fails. |

A valid header-only source is integrated into a header-only primary and fails `minimum_valid_rows`; `execute_dataset_build` maps every non-completed executor outcome to generic `{"status":"error","retryable":true}`. No `BuildResultStatus.NO_DATA`, reason code, or audit/supporting publication is returned, so an empty result is presented as retryable execution failure rather than a distinguishable completed NO_DATA outcome. | Detect zero valid rows and return a structured `NO_DATA` BuildResult with `valid_row_count=0` and no primary publication (or route it through the same audited NO_DATA package path as V1). | Stage a header-only GDC/Xena source, call `execute_dataset_build`, and assert `payload["result"]["status"] == "no_data"`, `valid_row_count == 0`, and no primary publication; current payload is `status == "error"`. |
| **B6** | **Important** | `backend/app/datasets/build/profiles.py:247-257`, `:270-287` | The V2 validation profile checks only the header column count. `csv.DictReader` silently stores extra fields under the `None` key, while `_check_rows` validates only named required fields. A primary row with an extra delimiter/column can therefore pass minimum rows, required fields, numeric, unit, and provenance checks and be published as malformed data. | Reject rows whose parsed field count differs from the schema/header count, including any `None` key or missing cells, before field checks. | Start from a valid primary, append an extra tab/comma field to one row, run the profile, and assert `ValidationResultStatus.FAILED`; current profile passes if the original named fields remain valid. |
| **B7** | **Important** | `backend/app/api/routes.py:839-840`, `:846-849`, `:889-901` | Artifact listing and download integrity checks use `path.read_bytes()` for the run manifest and every artifact. `FileResponse` streams only after the complete file has already been loaded into memory for hashing; a large published CSV can exhaust API process memory, and listing a task hashes every artifact eagerly. There is no artifact-size limit on this route. | Hash files incrementally in fixed-size chunks (and cache verified digests where appropriate) before returning `FileResponse`; enforce a configured size policy if required. | Create a multi-GB sparse/large artifact with a matching manifest, monkeypatch `Path.read_bytes` or measure memory during `GET /artifacts`, and assert the route hashes via bounded reads rather than loading the whole file. |

IDs are `pub_<build_id>_<digest-prefix>`, so digest order is unrelated to publication time. With chronological digests `f...` then `0...` then `a...`, the third build selects the first (`f...`) as `supersedes`, skipping the actual current second publication. | Select the prior record by authoritative `published_at` (or a durable current-publication pointer), not by publication ID string order. | Create three publication records with controlled timestamps/digest prefixes `f`, `0`, `a`; assert the third `_find_latest_publication` returns the second record's ID, not the lexicographic maximum. |

This makes NO_DATA indistinguishable at the tool boundary from any other completed package without a primary and forces the Agent to infer semantics from filenames, contrary to Phase 4a/4b's explicit result contract. | Add `build_result: manifest.build_result.model_dump(...)` (and an explicit outcome field) to the tool response for every completed run. | Run the fixture/no-expression pipeline and parse the returned JSON; assert `payload["build_result"]["status"] == "no_data"` and `reason_codes == ["no_primary_data"]`; current payload has no `build_result` key. |

## Overall risk read

The V1 validation/publish swap is comparatively defensive, but the merged V2 `execute_dataset_build` path has material trust-boundary and durability gaps: source changes can silently reuse stale checkpoints, publication directories do not preserve manifest paths, and the release gate does not bind all promoted bytes to the validated manifest. Empty V2 results and the V1 tool envelope also lose the explicit NO_DATA contract. Until B1-B5 and B9 are addressed, V2 output should not be treated as a reliable immutable publication path.
