## Findings

| ID | Severity | Location | Bug / concrete failure scenario | Fix direction | Reproduction sketch |
|---|---|---|---|---|---|
| A1 | Important | `backend/app/runtime/manager.py:1592-1606` | An unexpected worker exception while the run is already `CANCEL_REQUESTED` leaves the run permanently nonterminal. `_handle_worker_failure` only appends `run_failed` for `RUNNING`/`FINALIZING`; for `CANCEL_REQUESTED` it emits no terminal event and deliberately does not remove `_running`. If the cancellation waiter or executor then fails after the cancel request, no later path appends `run_cancelled`, so the task remains active and cannot be continued or deleted until a restart happens to recover it.` | Reconcile `CANCEL_REQUESTED` to exactly one terminal cancellation/interruption event in the worker-failure path and clear live ownership, or add a bounded cancellation fallback that guarantees terminalization. | Use an executor that raises after cancellation is requested; ensure the worker reaches `_handle_worker_failure` with `CANCEL_REQUESTED`, then assert the journal contains a terminal cancellation/interruption and `_running` is cleared. |
| A2 | Important | `backend/app/runtime/manager.py:1776-1802`, `backend/app/agent_loop/runner.py:1318-1356`, `:1508-1542` | Finalization can publish the filesystem package and emit `artifact_produced`/`publication_created` before `run_completed` is durable. A cancellation or process crash in that window leaves a valid `.runtime-publication.json` and publication event, but the run is `CANCEL_REQUESTED`/`FINALIZING`; the next manager recovery converts it to `run_interrupted`, and the API's manifest loader refuses the package because it requires a completed run. The user gets a non-success terminal run with a published package stranded on disk, while the event-sourced snapshot already contains a `current_publication_id` for a non-completed run.` | Make publication commit and terminal outcome a recoverable transaction: persist a finalize intent/commit marker and reconcile it on startup; order durable terminal state and publication exposure consistently, with one deterministic rule for cancellation racing publication. | Block or kill the process after `pending.publish()` and before `RunCompletedPayload`; restart and assert the run/publication/artifact state converges rather than producing `INTERRUPTED` plus an inaccessible published package. |
| A3 | Important | `backend/app/runtime/state.py:225-264` | The reducer accepts `publication_created` for any existing run, including `QUEUED`, `RUNNING`, `FAILED`, `CANCELLED`, and `FINALIZING`, and immediately updates `current_publication_id`. This is observable today because the completion callbacks emit `PublicationCreatedPayload` before the manager appends `RunCompletedPayload`; therefore the snapshot can temporarily claim a current publication while the run is not completed, and malformed/stale events can make a failed run appear published. The duplicate check also ignores `supersedes_publication_id`, despite publication records being intended immutable.` | Enforce the publication/run state contract and change the commit ordering or add a pending-publication state; compare all immutable publication fields on duplicate IDs and reject conflicting replays. | Reduce `RunQueuedPayload` then a `PublicationCreatedPayload` for that run and assert rejection; separately apply two same-ID publication events differing only in `supersedes_publication_id` and assert the second is rejected. Add an integration assertion for the actual completion event order. |
| A4 | Important | `backend/app/runtime/manager.py:1345-1418` | Recovery silently discards all pending HIL prompts. Every recoverable non-`QUEUED` run, including `AWAITING_USER_INPUT`, is immediately converted to `run_interrupted` with `reason="server restarted"`; the request ID/detail remain only in historical events and there is no resumed/closed prompt event. A browser that reconnects after a restart sees the old prompt in replay but the run is already terminal, so the visible correction/approval cannot be submitted and the user must start over. This is a cross-feature regression for 4c's durable pause/resume contract unless restart invalidation is explicitly intended and surfaced as a closed prompt.` | Either restore an awaiting run with a reattached input broker, or emit an explicit prompt-invalidated/interrupt outcome and make the frontend discard the stale prompt; document and test the selected restart semantics. | Persist `user_input_required(data_correction)`, stop the manager before resume, restart it, then submit the original request ID; assert either the same request resumes successfully or a durable prompt-invalidated outcome is present and the API returns the documented conflict. |
| A5 | Minor | `backend/app/runtime/manager.py:1297-1340`, `backend/app/subagents/input_broker.py:65-153` | `resume_run` routes to the global `SubagentInputBroker` before checking the parent task snapshot, run status, or the child record. A matching child request can therefore be accepted after the parent run has completed/cancelled (or while it is not awaiting main input), and the route returns the current snapshot as a successful 202. The normal terminal cleanup usually cancels child requests, but a cleanup race, independently emitted child request, or late request after a terminal event bypasses the main-run guard and can mutate a child after its owner is terminal.` | Load and validate task/run/child state first; only route a child resume while the parent is nonterminal and the child record has the matching pending request. Make terminal parent cleanup and broker removal share the same task lock. | Register a child input request, persist a parent terminal event, then call `resume_run` with that child request; assert a conflict/not-found response and no `subagent_input_resumed` event. Repeat with terminal cleanup racing the API call. |
| A6 | Minor | `backend/app/runtime/manager.py:759-760`, `backend/app/runtime/repository.py:255-257`, `backend/app/runtime/event_store.py:222-224` | Per-task lock/checkpoint registries retain entries forever. The manager's `_task_locks`, repository `_task_locks`, and `EventStore._checkpoints` all use task IDs as strong dictionary keys and are not purged by `delete_task`; repeated create/delete or imported-task workloads grow process memory even though the task directory and SQLite rows are removed. This is a long-lived service memory-growth path and is independent of event-log retention.` | Evict lock/checkpoint entries after deletion only when no operation is using them, or use a reference-counted/weak registry with a safe task lifecycle protocol. | Create and delete thousands of terminal tasks, then assert the three registries remain bounded rather than growing linearly with deleted task IDs. |
| A7 | Minor | `backend/app/runtime/index.py:316-354` | `TaskIndex.list_tasks` returns every active task regardless of the requested `limit`; the limit applies only to inactive history. Under many queued/running or stuck tasks, every API list call serializes an unbounded `active_items` array, and `_recover` uses the same active-first page repeatedly. This makes the task API and startup recovery scale with all active tasks and amplifies the impact of lifecycle states that fail to converge.` | Bound active results too, or introduce a separate active cursor/limit while preserving an explicit active/history contract. | Insert a large number of active summaries and call `list_tasks(limit=1)`; assert response size and query work are bounded and pagination can progress through active tasks. |
| A8 | Minor | `backend/app/runtime/state.py:387-401` | `artifact_count` is incremented for every `artifact_produced` event without identity deduplication. A retry/reconciliation path that appends the same artifact payload at a new task sequence makes the task/index count larger than the actual manifest; although Phase 4 removed the direct count-to-failure decision, the count remains part of the API/index and can mislead consumers or future admission logic. Publication events have explicit duplicate handling, but artifact events do not.` | Deduplicate by `(run_id, artifact_id)` or reject conflicting duplicate artifact identities; rebuild counts from the authoritative manifest/event set. | Apply identical `ArtifactProducedPayload` events at two distinct sequences and assert the projected count remains one; apply the same artifact ID with a different digest and assert rejection. |

## Overall Risk Read

The core per-task serialization and contiguous event-sequence checks are sound for the nominal path. The highest residual risk is at lifecycle failure boundaries: a cancellation-related worker failure can strand a run in `CANCEL_REQUESTED`, and publication can become durable before its terminal run state, producing stranded artifacts and an inconsistent event-sourced publication view. Phase 4c also does not survive manager restart with a usable pending prompt. Address A1-A4 before treating Phase 4 runtime behavior as production-safe; A5-A8 are lower-severity correctness and operability issues.
